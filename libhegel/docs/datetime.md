# Dates, times and time zones

**Status:** Implemented (engine, C ABI and the Rust frontend with its
`jiff`, `chrono` and `time` extras; the other frontends' mappings in §8.3
remain to do). Written 2026-10-16 from a survey of the engine, the seven
frontends, the property-based testing libraries in Appendix A and the
date/time libraries in Appendix B. The open questions were decided on
2026-10-17; §10 records the outcome. §4–§8 describe what was built, with
the places the implementation departed from the original text corrected
in place; the appendices are the original survey.

## Summary

Every Hegel frontend already draws dates, times and naive datetimes from
the engine, and that part of the design is sound: one integer node per
component, shrinking toward 2000-01-01 and midnight, shared by all seven
languages. Everything beyond it is missing or frontend-local: no
instants, no offsets, no durations, no time zones in the engine. Where a
frontend has time zones at all (Python, Java), it samples the host's zone
list by index, so a stored failure means a different zone on a machine
with a different tz database, nothing steers generation toward the
transitions where date bugs live, and gap and fold wall times are reached
by luck.

This proposal moves the whole date/time model into the engine, behind the
C ABI, so that each frontend is a thin mapping onto its native types:

1. **A bundled, pinned IANA time zone database** inside `libhegel`,
   preprocessed by a script into a small table (the way the Unicode tables
   are), with no new runtime dependency. The engine can then answer "what
   is the offset at this instant", "is this wall time unique, in a gap or
   in a fold" and "which transitions fall in this window" for every zone,
   identically on every machine.
2. **Time zones drawn as string nodes under a constraint**, so the choice
   sequence and the database carry the IANA name, a stored failure
   survives a tz database update, and shrinking walks a fixed ladder from
   exotic zones down to UTC.
3. **Zoned datetimes drawn wall-clock first** (zone, then civil datetime
   in that zone, then a fold bit only when the wall time is ambiguous),
   with a small fraction of draws targeted at the zone's transitions and
   at the calendar's own interesting values. Gap and fold times are
   generated deliberately and reported as such; a policy parameter avoids
   them for frontends whose types cannot hold them.
4. **Instants, UTC offsets, exact durations and calendar spans** as engine
   draws, plus a `precision` parameter on every time-bearing draw so a
   frontend with microsecond or millisecond types never truncates after
   the fact.
5. **Rust frontend:** a minimal first-party API exposes every engine
   value as a plain struct with no date arithmetic, parsing or
   conversions, so a user of any date library can wrap it; the `jiff` and
   `chrono` extras become complete (IANA zones, zoned datetimes, calendar
   spans) on top of it, and a `time`-crate extra is added. Other
   frontends get the same engine draws; their mapping is sketched in §8.

The engine takes no new dependency. `jiff` stays a dev-dependency and
becomes the oracle the engine's time zone code is tested against.

## 1. What this document settles, and what it does not

Settles: where date/time logic lives, the engine's value model and
ranges, how each value is encoded in the choice sequence (and so how it
shrinks and what the database stores), the time zone data source and its
update policy, the C ABI surface, and the Rust frontend API.

Does not settle: the exact API in the non-Rust frontends beyond the
mapping each needs (§8). Non-Gregorian calendars are out of scope: the
model is the proleptic Gregorian (ISO 8601) calendar only (§10, Q7), and
leap seconds appear only as a deferred generation knob for strings (§10,
Q6).

## 2. Where we are

### 2.1 Engine

`libhegel/src/native/draws/special.rs` has `Date` (proleptic Gregorian,
year in ±999,999), `Time` (nanosecond precision) and `DateTime`. The
date draw is one integer node holding the day offset from 2000-01-01,
clamped into the bounds; the time draw is one integer node of
nanoseconds from the lower bound; the datetime draw is a date node then a
time node whose bounds tighten on the boundary days. Civil arithmetic is
Hinnant's `days_from_civil` and its inverse. The three C ABI functions
`hegel_generate_date`, `hegel_generate_time` and `hegel_generate_datetime`
take inclusive bounds as `hegel_date_t` / `hegel_time_t` /
`hegel_datetime_t` structs.

There is no instant, offset, duration, period or time zone draw. The
engine is `#![no_std]` + `alloc` with a deliberately small dependency set
and ships as a cdylib, a staticlib and a wasm32 build for the TypeScript
frontend. Bundled data (the Unicode tables, the IANA TLD list) is
`include_str!` text, parsed once into a `Lazy`, regenerated by a script
under `just`.

Two engine facilities matter below. `draw_integer_from(kind, sampler)`
records an ordinary integer node whose fresh value comes from a custom
sampler, so a draw can be biased toward anything without the node being
forced or shrinking any differently. And a string node can carry a
`Constraint` (today `Grammar` or `Regex`) that validates the text on
replay, supplies a simplest value and gets its own shrinker pass; this is
the design `libhegel/docs/grammar-strings.md` describes.

### 2.2 Frontends

| Frontend | Today |
|---|---|
| Rust (`hegeltest`) | first-party `durations()` over `std::time::Duration` (u64 nanoseconds). `extras::jiff`: dates, times, datetimes, timestamps, spans (nanoseconds only), signed durations, offsets, and `zoneds()` as timestamp × time zone where the default time zone generator is UTC, the unknown zone, or a fixed offset. `extras::chrono`: naive dates/times/datetimes, fixed offsets, time deltas, naive weeks, weekday sets, `datetimes::<Tz>()` which draws a naive value and a `Tz` and rejects gaps with `assume(false)`, taking the earlier fold. No IANA zone is ever generated. |
| Python | `dates`, `times`, `datetimes(timezones=, allow_imaginary=)`, `timedeltas` (three integer nodes), `timezones()` = `sampled_from` over the host's sorted `zoneinfo.available_timezones()` with UTC first. Imaginary times are rejected after the fact. |
| Java | `dates`, `times`, `datetimes`, `zoneOffsets`, `zoneIds()` = `sampledFrom` over the JVM's zone list, `DateTimeGenerator.timezones(zones)` resolving with `ZonedDateTime.of` (gaps shifted, folds always earlier), `durations`. |
| Go | `Dates()` and `Datetimes()` returning UTC `time.Time`. |
| TypeScript | date, time and datetime as ISO 8601 strings. |
| OCaml, C++ | bind the three engine draws. |

The problems, concretely:

- **Zone choice is an index into a host-dependent list.** The Python and
  Java generators record the position of the zone in the host's list. The
  list differs between machines and tz database versions, so a database
  entry replayed elsewhere names a different zone, and the shrink target
  depends on what is installed.
- **Nothing targets transitions.** The chance that a uniformly drawn wall
  time in a year falls inside a given one-hour gap or fold is about
  1 in 8,800. Bugs around transitions are the bugs date code has.
- **Gaps and folds are resolved silently or rejected.** Java and chrono
  never produce the later fold; chrono rejects gaps; Python can produce
  them but only by luck.
- **Each frontend re-derives the same semantics.** Offsets, durations and
  fold handling are written per language, with different ranges and
  shrink targets.
- **Precision is an afterthought.** Python has microseconds, JavaScript
  milliseconds; truncating a nanosecond draw after the fact makes two
  distinct choice sequences produce the same value and wastes shrinking.

The rule in RFC-0001 (the monorepo proposal in `internal-rfcs`), that new
generator types should land in every language at once, is only
achievable if the engine does the work.

## 3. Requirements

R1. Every value the draws produce is valid in the engine's own model and
    carries enough information for every frontend to build its native
    value without re-deriving time zone rules.
R2. Generation and shrinking of time zones and zoned datetimes are
    identical on every machine, independent of the host tz database.
R3. A stored failure survives a tz database update as long as the zone
    still exists; a removed zone degrades to the simplest zone, not to an
    error.
R4. Gap wall times, both folds of ambiguous wall times, and the exact
    boundary instants of transitions are generated deliberately, at a rate
    a user can rely on, in every zone that has them.
R5. A frontend whose native type cannot represent a gap time (jiff,
    Temporal, Go, `std::chrono`) can ask the engine never to produce one.
R6. Shrinking has legible targets: 2000-01-01, midnight, UTC, zero
    duration, zero offset; a zoned datetime shrinks through the ladder
    "exotic zone → simple real zone → UTC", with the synthetic `Etc/`
    family and the legacy names ranked below every real zone so a
    minimal failure names a zone a reader recognises.
R7. Every time-bearing draw takes a precision, drawn in units of that
    precision, so no frontend truncates.
R8. Bounds are inclusive, and a draw with `min == max` is a constant, as
    Hypothesis and the existing engine draws behave.
R9. The engine gains no required runtime dependency, and the wasm build
    grows by the deflated table and the evaluator only (about 330 KB in
    the first release; there is no hard budget, since libhegel is
    expected to grow with its features until a concrete limit appears).
R10. Every surface a setting or a generator has today (builder, ABI,
    docs, `DefaultGenerator`) is reached before a generator counts as done.

## 4. The value model

The engine's model is the intersection every frontend's types can be
built from, with ranges wide enough that a frontend's bounds are never
clamped. Appendix B tabulates the libraries these were taken from.

| Engine type | Fields | Range | Shrinks toward |
|---|---|---|---|
| `Date` | year `i32`, month, day | year ±999,999 (unchanged; covers chrono's ±262,143, `time` with `large-dates`, and the ±9999 of jiff, Temporal and Python) | 2000-01-01, clamped |
| `Time` | hour, minute, second, nanosecond | 00:00:00 to 23:59:59.999999999 | lower bound (midnight) |
| `DateTime` | `Date` + `Time` | as above | 2000-01-01T00:00 |
| `Timestamp` | seconds `i64` since the Unix epoch, nanosecond `u32` | the civil range above, about ±3.2 × 10¹⁶ s; covers Temporal's ±10⁸ days, jiff, Noda Time, Python and chrono, not java.time's ±10⁹ years | 2000-01-01T00:00:00Z, clamped |
| `UtcOffset` | seconds `i32`, or *unknown* when the draw allows it | ±25:59:59, which is RFC 9636's recommended `utoff` range for TZif and jiff's and the `time` crate's envelope; Python's is ±24h exclusive, java.time's and Noda Time's ±18h | 0, known |
| `TimeZone` | IANA name as written (ASCII), plus the primary name it resolves to | the bundled database, or the caller's subset, plus `Etc/Unknown` when the spec allows it | `UTC` |
| `ZonedDateTime` | zone, `DateTime`, kind (unique / gap / fold), offset before and after the transition, fold (0/1), the resolved offset and whether it is known, and the `Timestamp` | as `DateTime` | zone ladder, then `DateTime` |
| `Duration` | seconds `i64`, nanoseconds `i32` with the same sign | ±i64 seconds (jiff `SignedDuration`, `time::Duration`, chrono `TimeDelta` fit; `std::time::Duration` is the non-negative half) | 0 |
| `Span` (calendar) | years, months, weeks, days, hours, minutes, seconds, milliseconds, microseconds, nanoseconds, each `i64` | per-unit bounds set by the caller; sign uniform or mixed | all zero |

Decisions worth calling out:

- **Fold, not DST flag.** Which of two candidate offsets a wall time means
  is "the earlier offset or the later one" (Python's `fold`, Temporal's
  `earlier`/`later`). It is not "is DST", which is wrong for Europe/Dublin
  and every other negative-DST zone.
- **Gap times are values.** A `ZonedDateTime` of kind `gap` carries the
  civil time that does not exist, the offsets on either side and the
  instant it resolves to under the one rule every library's default
  agrees on: interpret the wall time with the offset in effect *before*
  the transition, which shifts a gap time forward by the gap's length and
  picks the earlier instant in a fold (jiff and Temporal `compatible`,
  java.time `ZonedDateTime.of`, Noda Time's lenient resolver, PEP 495
  `fold=0`, `whenever`, RFC 5545; Appendix B). The resolved offset a gap
  value reports is the one in force at that shifted instant, the offset
  *after* the transition, so the value prints as an instant that exists
  (`2024-03-10T02:30:00-04:00[America/New_York][gap]`). A frontend whose
  type can hold the imaginary wall time (Python) uses the civil fields;
  one that cannot uses the instant, or derives the "shift backward"
  instant from the offsets if its library prefers that.
- **Offsets and zones are different generators.** A fixed offset is not a
  zone name, and a frontend that wants "UTC, a fixed offset or a region"
  composes the two with `one_of`, which keeps the branch index as the
  shrink dimension.
- **Unknown offset is a value.** RFC 3339's `-00:00` and RFC 9557's `Z`
  before a bracketed zone mean "instant known, local offset unknown"; the
  tz database has the `Factory` zone for it, CLDR names the zone
  `Etc/Unknown`, and jiff has `TimeZone::unknown()`. The offset draw can
  yield an unknown offset and the zone draw can yield `Etc/Unknown`, each
  behind an option that is off by default because most frontends' offset
  types cannot hold it. A `ZonedDateTime` in `Etc/Unknown` has a known
  instant, civil fields equal to UTC and an unknown offset, as CLDR and
  jiff specify. Both shrink to the known value: 0 and `UTC`. (§10, Q8.)
- **Instants shrink toward 2000-01-01T00:00:00Z, not the epoch**, so that
  a zoned datetime drawn through instant bounds and one drawn through
  wall-clock bounds agree, and so that a minimal instant prints as a date
  the reader recognises. (§10, Q3.)
- **Names are preserved, not canonicalised.** Temporal, `whenever` and
  jiff keep `Asia/Calcutta` as written and compare by primary identifier;
  the engine does the same and reports both names, so parsing code sees
  link names, and the primary name is there for frontends that need it.
- **No leap seconds in the model.** Second is 0..59, as in jiff, Temporal,
  java.time, Noda Time and Python. A knob for `23:59:60` in generated
  strings only is deferred to Phase 3 (§10, Q6).

## 5. Time zone data

### 5.1 Source and format

The engine bundles one pinned IANA release, preprocessed by
`scripts/generate_tzdata.py` (run as `just tzdata`, like `just
unicodedata`) into a text table under `libhegel/src/tzdata/`. The script
reads the compiled TZif files of a pinned `tzdata` PyPI release (the same
bytes `zoneinfo` would use), parses the version 2+ body and the footer
(RFC 9636), and emits per zone:

- the explicit transitions as `(unix seconds, offset seconds, is_dst,
  abbreviation)`,
- the footer rule already parsed into fields (standard offset, DST offset,
  start and end rules as month/week/weekday/seconds-after-midnight, with
  the `Jn` and `n` day forms and the signed transition hours in
  -167..167 that current footers use, such as Nuuk's `M3.5.0/-1` and
  Gaza's `M3.4.4/50`), so the engine contains an evaluator and no parser,
  and the evaluator extrapolates the rule to any year rather than
  stopping at 2037 or 9999,
- the link names that resolve to the zone,
- a classification computed by the script (§5.3).

Slim TZif for the whole database is about 200 KB (jiff-tzdb's
concatenated file is 207 KB for 2026e); the text table is larger and is
stored deflate-compressed (the engine already depends on `miniz_oxide`)
and inflated into a `Lazy` on first use. This keeps R9. Only the offsets
matter to generation, so the "main" versus "rearguard" distinction (which
changes only `isdst` flags and abbreviations, for Europe/Dublin and the
like) does not affect the table's semantics; the feature tags below are
derived from offset changes, never from `isdst`.

`hegel_tzdb_version()` returns the bundled release ("2026e"). Both the
text table and its deflated copy are checked in, so the table is
reviewable in the PR that regenerates it; the table carries its version
in its header and in `version.txt` beside it, and `checksum.txt` holds an
FNV-1a checksum of the text that the script writes with it. A test fails
if the script's pinned version and the table disagree, or the table is
not what the script would write (compared against the checksum, and
against a fresh run of the script when `uv` is installed; the `just
check-tzdata` CI step runs the script's `--check` mode). Both compare
the text table, the version and the checksum, and check that the
deflated copy inflates to the text table; the deflated bytes themselves
depend on the zlib build and are not compared. The engine reads only
the deflated copy. A TZif record that repeats the type before it (same
offset, flag and abbreviation) is left out of the table, except for a
zone's last record, which zic writes to pin where the footer rule takes
over and which the engine applies the footer from without reporting it
as a transition. The update policy is
the Unicode one: bump deliberately, in its own PR, with the changelog
naming the release.

### 5.2 Why bundle, and why not `jiff`

*Not the host database.* Reading `/usr/share/zoneinfo` (what jiff and
`zoneinfo` do) makes generation depend on the machine, fails R2, and is
unavailable on Windows and in wasm.

*Not `jiff` in the engine.* jiff is excellent and already a dev
dependency; it would give the TZif reader, the POSIX rules, transition
iteration and ambiguity resolution for free. Against it: the engine's
dependency set is deliberately minimal and the C library and wasm build
would carry a semver-0 dependency; jiff's civil range (±9999) is narrower
than the engine's envelope so we would keep our own calendar arithmetic
regardless; and the part we need, offset-at-instant plus
classify-wall-time plus transitions-in-window over a bundled database,
is a few hundred lines once the parsing is done offline. The decisive
point is testability: with jiff as the *oracle* (dev dependency, with
`tzdb-bundle-always` pinned to the same release) the engine's evaluator
is checked against an independent implementation over every zone and
every transition. If the evaluator proved harder than expected, switching
to `jiff` with `alloc` and `tzdb-bundle-always` is a contained change
behind the same engine API, and the doc records that as the fallback.

*Not frontends supplying transitions.* It would push the hard part back
into seven languages, which is the situation we are leaving.

### 5.3 Zone metadata for generation and shrinking

The script tags each zone with features drawn from the categories in
Hypothesis issue #69 (Appendix A.1):

fixed (no transitions after 1970), whole-hour offset, fractional offset
(:30, :45), seconds-precision offset (pre-standardisation local mean
time, and Africa/Monrovia's -00:44:30 until 1972), simple DST (one annual
pair of one-hour transitions), DST of another size (Lord Howe's 30
minutes, Troll's two hours), more than two changes in a year
(Morocco's Ramadan rule), base-offset change (Europe/Moscow 2011 and
2014), transitions at midnight (America/Sao_Paulo, Africa/Cairo), a
transition spanning midnight (Asia/Pyongyang 2015), a skipped or doubled
whole day (Pacific/Apia 2011, Pacific/Kwajalein 1993, Pacific/Kiritimati
1994), a transition with no offset change (Europe/Lisbon 1992), a
`-00` or `Factory` zone, link name, legacy name (`EST`, `EST5EDT`), and
the `Etc/GMT+5` inverted-sign family. Appendix C lists the zones each
tag was verified against.

From the tags the script also assigns each zone a **rank**, the shrink
ladder of R6, in tiers: `UTC`; then the simple real zones, the
`Area/Location` names whose tags other than `seconds` (pre-1970 local
mean time) and `link` are exactly `whole_hour` with `fixed` or with
`dst`, so a whole-hour offset that is fixed or has textbook one-hour DST
and no other irregularity after 1970 (`America/New_York` and
`Asia/Tokyo` qualify; `Europe/London` does not, for its `base_change`,
nor `Asia/Kolkata`, for its fractional offset); then every other
`Area/Location` name; then the fixed `Etc/` family by absolute offset;
then the legacy names (`EST`, `EST5EDT`, `US/Eastern`). Within a tier
names with fewer tags come first, so a zone precedes its links, and ties
break by name, so the ladder starts `UTC`, `Africa/Johannesburg`,
`America/Matamoros`, `Europe/Belgrade`, `Europe/Warsaw`,
`Indian/Maldives`, `Africa/Abidjan`, and a failure in a real zone
shrinks to a real zone rather than to `Etc/GMT+1`, whose sign reads
backwards. `UTC` is the primary zone and `Etc/UTC`, `Etc/GMT`, `GMT`,
`Zulu` and the rest of that family are links to it, as ECMA-402 has it.
The rank and the tags are data in the
table, reviewable in the PR that regenerates it, and the engine never
infers them at run time.

## 6. Engine draws

Each draw below is a spanned sequence of ordinary choice nodes. Nothing
new is added to the node kinds except one string constraint.

### 6.1 Time zone

`generate_timezone(spec)` draws one string node whose constraint is
`Constraint::TimeZone(spec)`. The spec is the allowed set of names (all
bundled names by default, with legacy names excluded and link names
included; or an explicit list from the caller), whether `Etc/Unknown` is
included (off by default), and whether an unknown name supplied by the
caller is accepted as an opaque zone (§8, version skew). `validate` is set
membership, and a stored name the spec no longer allows replays as the
lowest-ranked allowed name; `simplest` is that name too. An empty explicit
list is an argument error.

Fresh generation mixes two samplers: with probability ½ uniform over the
allowed set, so every zone is reachable and a name-parsing bug in a rare
link name is found; otherwise weighted by feature tags, so that zones with
fractional offsets, negative DST, a skipped day or a future rule change
are each drawn at a rate a short run reaches.

Shrinking adds one pass beside `shrink_grammar_strings`: try the simplest
name, then walk down the ladder from the current rank, accepting the first
replacement that keeps the failure. The generic string shrinker is not
applied (its deletions would never hit a valid name).

### 6.2 Zoned datetime

`generate_zoned_datetime(spec)` takes: the time zone spec, bounds that are
either civil (`DateTime` pair, applied to the wall clock in whatever zone
is drawn, as Hypothesis's naive mode and all the current frontends) or
instants (`Timestamp` pair), a precision, an **imaginary** policy (`allow`
or `avoid`) and an **ambiguous** policy (`both`, `earlier`, `later`).

The node sequence is: zone (6.1) · targeted? (boolean) · [target index ·
half-width] · date · time · [fold].

1. Draw the zone. A zone the engine cannot evaluate (an opaque name the
   spec accepted) reads its civil time as UTC with an unknown offset, as
   `Etc/Unknown` does.
2. Convert instant bounds into a wall-clock window in that zone: from the
   earliest wall time an instant in the bounds reads to the latest, which
   across a fold is the transition's wall time rather than a bound's own
   reading, and under `allow` includes the skipped wall times that shift
   to an instant in the bounds. The window of civil bounds is likewise
   narrowed to the wall times whose instants lie in the `Timestamp` range
   of §4. When the instant window holds no value at the precision, or
   spans at most a day and lies within two days of a transition, draw the
   instant instead as one integer node: an index into the values in the
   bounds in instant order (the wall times at the precision of each
   stretch of constant offset, trimmed of the repeat the ambiguous policy
   excludes, with a gap's skipped wall times under `allow`), shrinking
   toward the real wall time nearest 2000-01-01T00:00:00Z, never a
   skipped one, which denotes the same instant as a real one, and
   sampled at the
   targeting rate at either side of a transition or at an Appendix C
   instant. The instant fixes which repeat of a fold the value means, so
   no fold node follows. Hypothesis's aware mode found this fallback
   necessary and the reasons apply here unchanged. A drawn zone with no
   value in the bounds rejects the test case; bounds no allowed zone has
   a value in are an argument error.
3. Draw `targeted`, a boolean whose rate is a generation parameter drawn
   per test case with mean 5% (§10, Q4) the first time a zoned draw needs
   it, and recorded under a fixed weight so the node's kind is the same
   in every execution. Skip the node when no target lies in the window.
4. Targeted: pick a target from the zone's transitions in the window
   together with the global interesting instants (Appendix C), as an
   integer index shrinking toward the one nearest 2000-01-01; pick a
   half-width from {1 s + 1 unit, 1 h + 1 unit, 1 day}; the date and
   time bounds become that window around the target's wall time (for a
   transition, the wall time just after it), clamped, and the date and
   time are drawn uniformly within it, since the integer sampler's
   preference for the low end would otherwise reach one side of the
   transition only.
5. Draw the date and time nodes exactly as `generate_datetime` does, at
   the requested precision.
6. Classify the wall time against the zone. Unique: done. Fold with
   policy `both`: draw one boolean node, the fold. Gap with policy
   `allow`: report kind `gap`, both offsets and the forward-shifted
   instant. Gap with policy `avoid`: the time node's sampler redraws a
   wall time that lands in a gap, so fresh generation draws from the
   non-gap times of the day; a value that still lands in one (a replayed
   or shrunk value, or one on a day the clocks skipped entirely) is moved
   to the first wall time after the gap, or to the last wall time before
   it when that lies past the window, and a window lying within a gap
   rejects the test case. The draw never returns a gap under `avoid`.
7. Instant bounds: if the resolved instant is outside them (a fold on the
   wrong side of a bound), reject the test case as Hypothesis does; this
   can only happen within one transition's width of a bound.

The fold node exists only when the wall time is ambiguous, so a value
never carries a meaningless fold and the choice sequence has no dead
node, improving on Hypothesis's independently drawn fold. The cost is
that a repeated wall time's sequence is one node longer than a unique
one's, so it is the less simple of the two: under `both`, a shrink
whose lower bound lies in a fold ends at the first unique wall time
after the fold rather than at the bound, unless only repeated wall
times keep the failure.

### 6.3 Timestamps, offsets, durations, spans

- `generate_timestamp(min, max, precision)`: one integer node, count of
  precision units offset from 2000-01-01T00:00:00Z clamped into bounds;
  the sampler mixes uniform with the interesting instants of Appendix C
  and the transitions of every bundled zone (a footer rule's listed up to
  two centuries after the origin).
- `generate_offset(min, max, granularity, unknown)`: one integer node,
  count of granularity units, shrinking toward 0; granularity ∈ {hours,
  quarter-hours, minutes, seconds} is the unit, so the node's value is a
  value of the draw at any granularity as a time's is at any precision
  (§6.4); the sampler mixes uniform with
  the set of offsets any bundled zone has ever used (a few hundred
  values, from the table), so `+05:45`, `+12:45`, `-00:44:30` and the
  like appear. When `unknown` is allowed a weighted boolean node comes
  first and `true` yields the unknown offset; the count node is drawn
  either way, so that the unknown's choice sequence is no shorter than
  a known offset's and the draw shrinks to a known offset before the
  offset itself shrinks (a shorter sequence would be the simpler one).
- `generate_duration(min, max, precision)`: one integer node of units,
  shrinking toward 0.
- `generate_span(spec)`: one integer node per enabled unit, drawn largest
  unit first within its bounds, with a sign policy: `uniform` draws one
  sign node, only when the bounds admit a span of either sign other than
  zero, then magnitudes (jiff `Span`, Temporal `Duration`), `mixed` draws
  each component signed (java `Period`), `nonnegative` draws magnitudes
  only. As with the fold node of §6.2, a sign the bounds fix is not
  drawn, so the sequence has no dead node. The per-unit bounds are on
  the unit's signed value: under `uniform` a negative span draws each
  magnitude within `[max(-max, 0), -min]` and a non-negative one within
  `[max(min, 0), max]`, `nonnegative` requires every `min` to be at least
  0, and a spec with no enabled unit is an argument error. Shrinks to the
  zero span.

The timestamp and offset samplers draw their targets at the same per-case
rate as §6.2's `targeted` node. The timestamp catalogue lists the
transitions of the primary zones (a link shares its zone's), and the
duration sampler targets the bounds and a few round durations (one unit,
a second, a minute, an hour, 23, 24, 25 and 36 hours, a week, a year, the
`i32` seconds and `i64` nanoseconds limits) of either sign.

### 6.4 Dates, times, datetimes

`generate_date` is unchanged in encoding. Two additions: the sampler mixes
in the interesting dates of Appendix C (Feb 29 nearest the bounds, the
year boundaries, the 2038 and 2106 overflow days, the ISO-week-53 days,
the Julian-to-Gregorian cutover), and the bounds may be narrowed by a
weekday mask and a month mask, applied by snapping the drawn day to the
nearest allowed day inside the bounds, toward 2000-01-01 on a tie, rather
than by rejection (jqwik's post-filter is the thing to avoid); bounds
holding no allowed day are an argument error. `generate_time` and
`generate_datetime` gain `precision`; a time's node becomes a count of
units, so a microsecond frontend and a nanosecond frontend draw the same
node shape.

### 6.5 Printing and reporting

The engine already prints choice nodes for its own diagnostics; the new
draws print as RFC 9557 strings
(`2024-03-10T01:30:00-05:00[America/New_York]`) with the resolved offset,
`[gap]` appended to a skipped wall time
(`2024-03-10T02:30:00-04:00[America/New_York][gap]`) and `[fold=0]` or
`[fold=1]` to a repeated one, an unknown offset as `-00:00` and
the unknown zone as `Z[Etc/Unknown]` (jiff's spelling), so a counterexample in any frontend's
output can be read without knowing that frontend's type. The Rust
frontend prints a duration in the ISO 8601 form (`PT1H30M5.5S`) and a
span in jiff's friendly form (`1y 2mo 3d`).

## 8. Frontends

### 8.1 Version skew

The engine's bundled release and the host library's database will
differ by up to a few months. The contract: the engine decides *what to
generate*; the host library decides *what the value means*. A frontend
builds its native value from the civil fields, the zone name and the fold
(or, for a gap, from the shifted instant), never by trusting the engine's
offset. If the host's rules disagree the value is still valid, merely not
the targeted edge. Frontends that can enumerate the host's zone names
pass them as the spec's explicit subset, so a name the host cannot
resolve is never drawn; where they cannot, an unresolvable name is
rejected with `assume`. `hegel_tzdb_version` lets a frontend compare the
two releases. The Rust extras document the skew rather than warn about
it: chrono-tz compiles in its own release (`chrono_tz::IANA_TZDB_VERSION`),
so the two differ on every run between its releases and a warning would
be noise, and jiff and `time` cannot report a release at all. A frontend
whose host database is updated independently (Python's `tzdata`, the JVM)
can warn once per run when the two differ.

### 8.2 Rust

`hegel::datetime` module of plain value types mirroring §4 one to one
(`Date`, `Time`, `DateTime`, `Timestamp`, `UtcOffset`, `TimeZone`,
`ZonedDateTime`, `SignedDuration`, `Span`), each a public struct of
public fields (`UtcOffset` is the enum `Known(i32) | Unknown`) deriving

## 10. Decisions

The questions the proposal left open, as put on 2026-10-16, and the
decisions taken on 2026-10-17. This file is the record; no RFC is filed
in `internal-rfcs`.

Q1. Default zone set: every name including links (Hypothesis) or
    canonical zones only, with links behind an option? **Decided:** links
    on, legacy names off, both switchable in the spec.
Q2. Should the Rust first-party API expose plain engine value types so
    users without jiff or chrono get dates, or stay with extras only?
    **Decided:** a minimal first-party API that exposes the data and
    nothing more: plain structs for every §4 value, with no convenience
    date-time API, for users with another date library to wrap (§8.2).
Q3. Shrink target for instants: 2000-01-01Z or the Unix epoch.
    **Decided:** 2000-01-01Z.
Q4. The targeted-draw probability: fixed 5%, or a generation parameter
    drawn per test case like the integer category weights. **Decided:**
    a generation parameter with mean 5%.
Q5. Breaking `hegel_generate_time`/`hegel_generate_datetime` for
    precision versus new names. **Decided:** break, with the changelog
    note.
Q6. Leap seconds: a `leap_seconds` knob on times that yields second 60
    (chrono's `NaiveTime` and the Haskell `time` tests can hold it; no
    other target can), off by default. **Decided:** as proposed, Phase 3
    at the earliest, and only in generated strings.
Q7. Non-Gregorian calendars (Temporal's `u-ca`, Noda Time's calendar
    systems, java.time's `chrono`). **Decided:** out of scope. The model
    is ISO 8601 (proleptic Gregorian) only; frontends with calendar
    systems convert from it.
Q8. An "unknown offset" value (RFC 3339's `-00:00`, jiff's `Etc/Unknown`,
    the tz database's `Factory` zone) as a first-class output of the
    offset and zone draws, or frontend composition as the jiff extra does
    today? **Decided:** first class, behind an option that is off by
    default (§4, §6.1, §6.3, §7, §8.2).

### A.1 Hypothesis in detail

The reference design, read from
`hypothesis/strategies/_internal/datetime.py` and the changelog.

- **Capped multipart draw.** Components are drawn largest to smallest
  (year, month, day, hour, minute, second, microsecond); each is capped
  by the bound's component only while every previous component has
  equalled that bound's component; the day's upper limit is the real
  month length computed branch-free so that no rejection is needed and
  symbolic backends do not branch. Year shrinks toward 2000, the rest
  toward their minimum. Since 5.8.1 this replaced "days since
  2000-01-01" for dates. `fold` is drawn as an independent integer
  *last*, even when the wall time is not ambiguous; the source says tying
  it to the zone "would require very invasive changes ... at the cost of
  efficient shrinking". `timedeltas` uses the same capping over days,
  seconds, microseconds.
- **Two modes.** Naive bounds: draw the wall time, attach the drawn
  tzinfo. Aware bounds (6.158.0, 2026-07): bounds are instants; the
  wall-clock window in the drawn zone is computed, and when the window
  inverts, or is a day or shorter and touches an ambiguous endpoint, the
  draw falls back to UTC-then-convert. Out-of-bounds folds are rejected.
- **Tricky datetimes (6.168.0, 2026-09-08, closing issue #69 from 2015).**
  5% of draws target an interesting instant: 28 hard-coded leap-second
  boundaries, the Unix epoch, 2000-01-01 and 2038-01-19T03:14:08, plus
  the zone's transitions, which are discovered by *probing* the tzinfo
  object at six-day steps between 1800 and 2050 and bisecting to the
  second (the shortest real inter-transition gap is just under seven
  days: Brazil, October 2000). The instant index shrinks toward the one
  nearest 2000-01-01; a half-width is drawn from (1 s + 1 µs, 1 h + 1 µs,
  1 day); the capped draw then runs over that wall-clock window, which is
  what makes gap times, both folds and exact boundary microseconds
  reachable.
- **Imaginary times.** The oracle is a round trip through UTC. The
  default allows them "because malformed timestamps are a common source
  of bugs"; `allow_imaginary=False` rejects.
- **Zones.** `timezone_keys()` is `("UTC", *sorted(available_timezones()))`
  filtered to keys that exist on disk, with `posix/` and `right/`
  prefixed names as `one_of` branches so the branch index shrinks to
  "no prefix"; within a branch it shrinks to `UTC` then alphabetically
  (`Africa/Abidjan`). Issue #2414 (open) proposes grouping zones into
  fixed, whole-hour, simple DST and weird so shrinking walks that
  ladder; the source carries a TODO to "place a higher priority on
  'weird' timezones". Issue #1203 declined a granularity parameter in
  favour of `map`, with the rule sketched that a unit must be an integer
  factor of the next unit up.
- **Warts noted in the source.** pytz's `localize(is_dst=...)` mapping
  from fold is wrong for negative-DST zones; the generated zone set
  "may vary depending on the configuration of your machine"; the
  leap-second table has a "keep in sync" comment.

### A.2 Ideas adopted here, and from where

Wall-clock-first draws with a fold bit and a UTC fallback for degenerate
windows (Hypothesis); a small targeted-draw probability with three
half-widths and an instant index that shrinks toward 2000 (Hypothesis);
`allow_imaginary` defaulting to allow (Hypothesis); a ladder of zone
groups as the shrink order (Hypothesis #2414, Kotest's transition
classifier); precision as a draw unit rather than a post-hoc truncation
(jqwik `ofPrecision`, scalacheck-toolbox `Granularity`); calendar edge
cases as biased special values (Kotest, ScalaCheck's `calendar`, jqwik);
`min == max` as a constant and `datetime`-where-`date`-expected as an
error (Hypothesis); overflow-safe offset ranges near the representable
edges (Hedgehog.NET); a separate "zone names" generator so parsing code
sees link and legacy names (Hypothesis `timezone_keys`); synthetic zones
with explicit transitions as a future generator (NodaTime.Testing).

### A.3 Mistakes avoided

Resolving gaps and folds silently (`atZone`, `ZonedDateTime.of`: Kotest,
scalacheck-toolbox) or rejecting gaps and never producing the later fold
(jqwik); attaching an independently drawn offset to a UTC value and
calling it zoned (chrono's `arbitrary`); offset ranges that are either
unrealistic (±24 h with seconds) or too narrow (jqwik's 15-minute
multiples, FsCheck's quirks at ±12/+14) without saying which; defaults
tied to the system clock (Kotest's kotlinx arbs, which also never
produce Dec 31 of a leap year); shrinking toward 1900, 1970, year 1 or
MJD 0; post-filtering month and weekday constraints (jqwik) with a
feasibility check to avoid empty filters; a fold bit that is set when
meaningless (Hypothesis, by its own admission); leap seconds generated
with no opt-out (chrono); depending silently on the host tz database
(every JVM library, `zoneinfo`, jiff by default).

### B.1 The resolution consensus

Every library's default or lenient behaviour is one rule: interpret the
wall time with the offset in effect *before* the transition. In a fold
that picks the earlier instant; in a gap it pushes the wall time forward
by the gap's length. jiff's `AmbiguousOffset` documents `compatible` as
"take `before` for both Gap and Fold"; Temporal's `'compatible'`,
java.time's `ofLocal`, Noda Time's `LenientResolver` (since 2.0), PEP 495
`fold=0`, dateutil's `resolve_imaginary`, `whenever`'s `"compatible"` and
RFC 5545 coincide. The engine's output carries both offsets so a frontend
can implement `earlier`, `later`, `reject` or `prefer(offset)` from them:
"earlier in a gap" means shift *backward* (Temporal, `whenever`), which
is not the same as Noda Time's "end of the interval before".

### B.2 Names and offsets in strings

Temporal, `whenever` and jiff's tzdb preserve the identifier as written
(`ASIA/calCuTTa` becomes `Asia/Calcutta`, not `Asia/Kolkata`) and compare
by primary identifier; ECMA-402 requires every tz `Zone` to be primary
and every `Link` non-primary, with `UTC` primary and `Etc/UTC`, `Etc/GMT`
and `GMT` resolving to it. RFC 9557 (IXDTF) adds `[Zone]` and `[u-ca=]`
annotations with a `!` critical flag to RFC 3339 and redefines `Z` with a
bracketed zone as "instant known, local offset unknown", so
`...Z[Europe/Paris]` is consistent and must be re-resolved; jiff,
Temporal and `whenever` implement this; Elixir rejects `-00:00`, Python
accepts it as zero. When a string carries both an offset and a zone, jiff
and Temporal reject a mismatch by default (`OffsetConflict::Reject`,
`offset: 'reject'`) and compare hour-and-minute offsets against the zone's
offset rounded to the nearest minute, exact when the offset has seconds
(`-00:44:30[Africa/Monrovia]` accepted, `-00:45[...]` rejected).

### B.3 Time zone data sources

jiff: `TZDIR`, then the system directories, then Android's concatenated
file, then the bundled `jiff-tzdb` (slim TZif, rearguard data, 207 KB for
2026e, `no_std`, zero dependencies, `get(name)` and `available()`), with
`tz-fat` expanding transitions in memory. Temporal: the host's ICU/CLDR
data. java.time: `tzdb.dat` in the JDK. Noda Time: an embedded `.nzd`
compiled by `NodaTime.TzdbCompiler`, with `TzdbVersion` and an updatable
stream. `whenever`: its own Rust TZif parser over `PYTHONTZPATH` and the
`tzdata` package. Python `zoneinfo`: `TZPATH` then `tzdata`, excluding
`posix/` and `right/`, 598 keys on a full install including `backward`
links. Go: `ZONEINFO`, the system, `$GOROOT/lib/time/zoneinfo.zip`, then
`time/tzdata` (about 450 KB) if imported. chrono-tz and time-tz: compiled
in at build time (chrono-tz 0.10.4 ships 2025b, three releases behind).
Elixir `tz`: periods precomputed five years ahead, then rule evaluation.

## Appendix D. The tz database, as the evaluator needs it

- **Releases.** Latest at the time of writing is 2026e (2026-09-29);
  2026b through 2026e each changed a Canadian province's or Morocco's
  rules. There is no schedule; ECMA-402 says five to ten releases a year.
  `zone1970.tab` has 312 rows, `zone.tab` 418, `backward` 252 links; a
  full install exposes 598 keys to Python.
- **TZif (RFC 8536, obsoleted by RFC 9636).** A version-1 block with
  32-bit transition times (1901-12-13 to 2038-01-19), then for version 2+
  the same with 64-bit times and a footer holding a POSIX TZ string.
  `utoff` is seconds east of UT and "SHOULD be in [-89999, 93599]";
  transitions are strictly ascending; before the first transition type 0
  applies, after the last the footer applies. Version 3 lets the footer's
  transition hours be signed and range −167..167 and expresses all-year
  DST as `0/0,J365/25`; version 4 allows a truncated or expiring
  leap-second table. `zic -b slim` has been the default since 2020b, so
  explicit transitions stop at the last rule change and the footer
  carries the future; `-b fat` writes explicit transitions through 2037.
- **Footer forms seen in current data.** `EST5EDT,M3.2.0,M11.1.0`;
  `GMT0BST,M3.5.0/1,M10.5.0`; `IST-5:30`; `<+0330>-3:30`; `<+13>-13`;
  `<+00>0`; `<-02>2<-01>,M3.5.0/-1,M10.5.0/0`; `<-04>4<-03>,M9.1.6/24,M4.1.6/24`;
  `EET-2EEST,M4.5.5/0,M10.5.4/24`; `EET-2EEST,M3.4.4/50,M10.4.4/50`;
  `<+1245>-12:45<+1345>,M9.5.0/2:45,M4.1.0/3:45`;
  `<+1030>-10:30<+11>-11,M10.1.0,M4.1.0`; `<+00>0<+02>-2,M3.5.0/1,M10.5.0/3`.
  POSIX offsets are west-positive, which is why `Etc/GMT+5` is UTC−5.
- **Main against rearguard.** Since 2018e the main data models
  Europe/Dublin, Europe/Prague (1946–47) and Africa/Windhoek (1994–2017)
  with negative DST; the rearguard format keeps positive DST for parsers
  that cannot cope (ICU, historically Java, jiff by choice). The two
  differ only in `isdst` and abbreviations, never in offsets.
- **Source-format facts that reach the binary.** The first line of every
  location is local mean time with seconds precision; sub-second offsets
  exist in the source (`-0:25:21.1` for Dublin) but not in TZif. Rule
  times may exceed 24 hours or be negative. Zone names are
  `Area/Location` with components of at most 14 characters, no name a
  path prefix of another.
- **Leap seconds.** `leap-seconds.list` in 2026e expires 2027-06-28; the
  last positive leap second was 2016-12-31. `right/` zones embed the
  table; no library in Appendix B models leap seconds.
