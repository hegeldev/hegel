This is a reference for `libhegel`, Hegel's engine, and for the C ABI it exposes. It is intended to be detailed enough that you could write a Hegel <Def id="library">library</Def> for a new language only by referencing this document.

`libhegel` is a Rust port of Hypothesis's conjecture engine, built as a shared library (`libhegel.so`, `libhegel.dylib`, `hegel.dll`) with a C ABI. Every Hegel library — including [hegel-rust](https://github.com/hegeldev/hegel-rust), which has no special access — drives the engine through exactly the functions described here.

:::note
The canonical definition of the ABI is the header `hegel-c/include/hegel.h` in [hegel-rust](https://github.com/hegeldev/hegel-rust/tree/main/hegel-c), generated by `cbindgen` from the Rust source. Where this page and the header disagree, the header is right — please [tell us](https://github.com/hegeldev/website/issues/new).
:::

## Terminology

* <strong><span id="def-engine">Engine</span></strong>: `libhegel` itself. It owns generation, shrinking, the example database, and the decision of what to run next.
* <strong><span id="def-library">Library</span></strong>: the language-specific frontend that calls the <Def id="engine">engine</Def> — `hegel-go`, `hegel-cpp`, and so on. Sometimes called the *caller* below, since from the engine's point of view it is simply whoever is making the calls.
* <strong><span id="def-context">Context</span></strong>: an opaque handle that a failed call writes its diagnostic message onto. Passed as the first argument to nearly every function.
* <strong><span id="def-run">Run</span></strong>: the full lifecycle of one property test, including executing many <Def id="test-case">test cases</Def> and shrinking any failures.
* <strong><span id="def-test-case">Test case</span></strong>: a single execution of the test function, together with the concrete values generated for it. The <Def id="library">library</Def> drives one test case at a time.
* <strong><span id="def-family">Family</span></strong>: a <Def id="test-case">test case</Def> handle and all clones descended from it. Handles in a family are independent views onto one shared underlying test case.
* <strong><span id="def-span">Span</span></strong>: a labeled grouping of draws, opened and closed by the <Def id="library">library</Def>, that tells the shrinker which draws belong to one structure.
* <strong><span id="def-blob">Reproduce blob</span></strong>: a base64 string encoding a test case's choice sequence, which can be replayed later to reproduce it exactly.

## Calling convention

Every function takes a `hegel_context_t*` as its first argument and returns a `hegel_result_t` code, with two exceptions: <Fn name="hegel_context_new" />, which returns a context, and <Fn name="hegel_context_last_error" />, which returns the message pointer directly.

`HEGEL_OK` is zero and every error is negative, so `result != HEGEL_OK` (or `result < 0`) tests for failure. Anything else a call produces — a handle, a string, a count — is written through a trailing out-parameter named `out_*`.

A `NULL` context is always allowed, and simply opts out of error messages: the call still returns its usual error code, there is just nothing to read back. A context must not be used concurrently from multiple threads, since each fallible call overwrites the stored message. One context per test, or per thread, is the expected usage.

## Ownership

Pointers you pass *into* a libhegel function are always yours. The library reads them during the call and copies whatever it needs to keep, so you may free or reuse the memory as soon as the call returns. This covers strings, byte buffers, and arrays of strings alike.

Of the pointers libhegel hands *back*, you own — and must release with the matching free — every handle from these:

| Constructor | Free |
| --- | --- |
| `hegel_context_new` | `hegel_context_free` |
| `hegel_settings_new` | `hegel_settings_free` |
| `hegel_run_start` | `hegel_run_free` |
| `hegel_test_case_from_blob` | `hegel_test_case_free` |
| `hegel_next_test_case` | `hegel_test_case_free` |
| `hegel_test_case_clone` | `hegel_test_case_free` |
| `hegel_run_result` | `hegel_run_result_free` |
| `hegel_run_result_failure` | `hegel_failure_free` |
| `hegel_string_generator_*` | `hegel_string_generator_free` |
| `hegel_generate_bytes` | `hegel_generate_bytes_result_free` |
| `hegel_generate_string` | `hegel_generate_string_result_free` |

Every *other* pointer libhegel hands back is a borrowed string: libhegel still owns it, you must not free it, and it is valid only until a documented point. Strings read off a result or failure snapshot live until that snapshot's free; <Fn name="hegel_context_last_error" /> is invalidated by the next call on that context.

Result and failure snapshots own their data and are independent of the run they came from: they stay valid after <Fn name="hegel_run_free" />, so a wrapper can free each object from its own finalizer, in any order.

## Settings

A settings handle is built up with setters, handed to <Fn name="hegel_run_start" />, and then freed. Settings can be reused across runs; the engine reads them at run-start time and the run does not keep the handle alive.

A configured handle may be shared across threads, but the setters mutate it, so each setter call requires exclusive access.

## Run lifecycle

A run is a pull loop. The caller starts a run, repeatedly asks for the next test case and reports its outcome, and finally reads the aggregate result.

There is no background thread. The run handle owns the suspended engine as a future, and each <Fn name="hegel_next_test_case" /> call resumes it on the calling thread until it offers the next test case or finishes. All the engine's work — database replay, generation, targeting, shrinking, the final replay — happens inside those calls.

```c
hegel_context_t *ctx = hegel_context_new();

hegel_settings_t *settings;
hegel_settings_new(ctx, &settings);
hegel_settings_set_test_cases(ctx, settings, 200);

hegel_run_t *run;
hegel_run_start(ctx, settings, NULL, NULL, &run);

for (;;) {
    hegel_test_case_t *tc;
    if (hegel_next_test_case(ctx, run, &tc) != HEGEL_OK) break;
    if (tc == NULL) break;              /* the run is finished */

    /* Run the user's test body against `tc`, drawing values from it,
     * then report what happened. */
    hegel_mark_complete(ctx, tc, HEGEL_STATUS_VALID, NULL);
    hegel_test_case_free(ctx, tc);
}

hegel_run_result_t *result;
hegel_run_result(ctx, run, &result);
/* ... inspect the result, replay any failure blobs ... */

hegel_run_result_free(ctx, result);
hegel_run_free(ctx, run);
hegel_settings_free(ctx, settings);
hegel_context_free(ctx);
```

### Choosing an origin string

The `origin` passed to <Fn name="hegel_mark_complete" /> is load-bearing for shrinker quality. Two failures with identical origins are treated as the same bug and shrunk together; failures with different origins are treated as distinct bugs and the shrink budget is *partitioned* across them.

In particular, a library that recovers from a host-language exception to report a failure **must not** pass the recovered exception value (or its stringification) as the origin if that value depends on the failing draw. Every distinct draw would then look like a fresh bug and the shrinker would never converge.

The conventional shape is `"Panic at <file>:<line>"` — derive the origin from the *location* of the failing assertion, not from the assertion's message.

## Draws

Every draw takes a test-case handle and writes its value through an out-parameter. All of them can return `HEGEL_E_STOP_TEST`, meaning the engine has exhausted its choice budget for this test case: abort the test body and call <Fn name="hegel_mark_complete" /> with `HEGEL_STATUS_OVERRUN`.

## Results and failures

## Replaying a blob

Replaying a <Def id="blob">reproduce blob</Def> is how a library performs the *final replay* of a counterexample: re-running the minimal failing test case so it can display the drawn values and re-raise the test's own failure.

There is no run handle and no engine run involved. The caller drives the returned test case with the usual per-test-case primitives, concludes it with <Fn name="hegel_mark_complete" />, and decides for itself whether the blob reproduced the failure (the property failed again) or is stale (it passed). Replay several blobs by calling this once per blob.

<FnTable name="hegel_test_case_from_blob" signature={`hegel_result_t hegel_test_case_from_blob(hegel_context_t *ctx,

                                           void *user_data,
                                           hegel_test_case_t **out_test_case)`}
  params={[
    {name: "blob", description: <>A base64 blob from <Fn name="hegel_failure_reproduction_blob" />.</>},
    {name: "callback / user_data", description: <>Where this replay's output goes, with the same contract as <Fn name="hegel_run_start" />. At debug verbosity the blob is decoded with a trace line, emitted synchronously during this call. The callback is only ever invoked on this thread and need not outlive the call.</>},
    {name: "out_test_case", description: <>Receives a caller-owned test-case handle, released like any other with <Fn name="hegel_test_case_free" />.</>},

## Threading

The three handle kinds have different threading contracts:

- A **context** must not be used concurrently from multiple threads. Each fallible call overwrites its stored message, so sharing one across threads is a data race.
- A **settings** handle may be shared across threads once configured, but each setter call requires exclusive access.
- A **run** handle must only be used from one thread at a time. Calling <Fn name="hegel_next_test_case" />, <Fn name="hegel_run_result" />, or <Fn name="hegel_run_free" /> concurrently on the same run is undefined behavior — in particular, do not free a run from a garbage-collector finalizer thread while another thread may still be using it.
- A **test-case** handle may be driven by at most one thread at a time, but unlike a run it *detects* misuse: concurrent operations may return `HEGEL_E_CONCURRENT_USE`. To generate from several threads, <Fn name="hegel_test_case_clone" /> the handle and give each thread its own clone.

export function FnTable({ name, signature, params, returns, notes }) {
  return (
    <details class="fn-details" id={`fn-${name}`}>
      <summary><code class="fn-summary-name">{name}</code></summary>
      <table class="fn-table">
        <tr>
          <td class="fn-label">signature</td>
          <td colspan="2"><pre class="fn-signature"><code>{signature}</code></pre></td>
        </tr>
        {params && params.map((p, i) => (
          <tr>
            {i === 0 && <td rowspan={params.length} class="fn-label">parameters</td>}
            <td class="param-name">{p.name}</td>
            <td>{p.description}</td>
          </tr>
        ))}
        {returns !== undefined && (
          <tr>
            <td class="fn-label">returns</td>
            <td colspan="2">{returns}</td>
          </tr>
        )}
        {notes !== undefined && (
          <tr>
            <td class="fn-label">notes</td>
            <td colspan="2">{notes}</td>
          </tr>
        )}
      </table>
    </details>
  );
}

export function EnumTable({ values }) {
  return (
    <table class="enum-table">
      {values.map((v) => (
        <tr>
          <td class="enum-name"><code>{v.name}</code></td>
          <td class="enum-value"><code>{v.value}</code></td>
          <td>{v.description}</td>
        </tr>
      ))}
    </table>
  );
}
